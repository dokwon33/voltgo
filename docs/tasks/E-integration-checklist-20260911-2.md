## 이미 구현한 E 기능

- 사용자 선택 후 `confirm_plan`에서 최신 충전 상태·시간으로 재검증한다. 계획 선택에 추가 승인 창은 없다.
- `save_preferences`만 HITL 승인·거절로 재개한다. 요청 후 120초를 넘으면 저장을 거부한다.
- 사용자 ID별 JSON 파일에 선호를 저장하고, 소유자 확인·사용자별 잠금·원자적 파일 교체를 적용한다.
- `delete_preferences`와 저장된 선호의 다음 대화 반영이 구현돼 있다.
- 입력 검사, 모델·도구 호출 한도, 읽기 도구 재시도, 존재하지 않는 후보 제거 미들웨어가 있다.
- 로컬 웹에는 저장 내용·승인 만료 표시, 승인 요청 ID 전달, 중복 결정 방지, 목적지 지도·변경 UI가 연결돼 있다.

현재 E 과제는 **프론트 결과 공유, 실제 모델로 승인·선호 흐름 확인, 발표 준비**다.

## 지금 바로 할 수 있는 일

1. 승인·선호 시연을 녹화한다: 저장 요청 → 거절 시 미저장 → 다시 요청·승인 → 새 대화에서 기억 → 삭제.
2. 확정·변경 흐름을 발표 화면으로 정리한다: 목적지 확정 → 지도 → 다른 후보로 변경. 지도 실연동은 키와 D의 경로 좌표 준비 후 확인한다.
3. E 발표 슬라이드를 만든다: 저장만 HITL, 120초 만료, 사용자별 JSON 기억, 호출 한도·재시도·후보 검증의 실제 구현과 시연 결과.
4. TMAP 지도 사용 권한이 있는 앱 키를 로컬에 설정할 수 있다면 배경 지도·마커를 실연동 점검한다. 키 발급과 실제 경로 좌표는 각각 별도 준비가 필요하다.

## 우선순위 1 — 현재 로컬 결과를 Git에 반영

- 프론트·웹 서버·관련 테스트를 별도 추가 작업 브랜치에 커밋하고 PR로 공유한다.
- 최근 `confirm_plan`의 A → B → A 목적지 변경 수정과 회귀 테스트를 포함한다.
- `.env`와 사용자 선호 데이터는 포함하지 않는다.
- 완료 기준: 다른 팀원이 해당 브랜치를 받아 현재 화면과 목적지 유지·변경 흐름을 실행할 수 있다.

## A 작업 반영 후 — E의 승인 화면 연결 확인

A 브랜치에 이미 `config_for(user_id, thread_id)`, `bind_session`, 승인 `request_id` 발급·재전송 처리가 있다. 이 로직을 별도로 중복 구현하지 않는다.

웹에서 맞출 부분:

1. `scripts/web.py`의 `envelope()`는 현재 원래 `thread_id`로 승인 checkpoint를 조회한다. A 통합 후에는 `config_for(context.user_id, thread_id)`로 조회해야 한다. 함수 인자만 추가해선 승인 창 복원이 연결되지 않는다.
2. 승인 ID는 코어의 `response.request_id` / `session.pending_request_id`를 사용한다. 새로고침·대화 복원 때도 같은 ID를 유지한다.
3. 웹의 `approval_tokens`, `decision_results`와 A의 `approval_requests`가 서로 다른 요청을 가리키지 않도록 결과 반환·재전송 정책을 맞춘다.
4. A는 `confirmed_by_request`를 `confirmed_by_plan`으로 바꾼다. 통합할 때 로컬의 A → B → A 재검증 수정을 유지한다.
5. 계획 조건 변경과 선호 승인 만료 시각을 분리하는 A의 변경을 유지한다.

완료 기준: 승인 화면 새로고침, 동일 ID 승인 재전송, 같은 ID의 다른 결정, 연속된 새 승인 요청에서 저장이 한 번만 실행되고 올바른 요청이 표시된다.

## 보석님 담당 — 접속자별 웹 격리

main의 선호 파일 분리와 A 브랜치의 checkpoint 분리는 기반 기능이다. 웹은 모든 접속자에게 하나의 `VOLTGO_USER_ID`를 넣으므로, A 브랜치를 합치는 것만으로 접속자 격리가 완성되지 않는다.

- 웹 서버가 접속자 세션을 발급·검증하고 그 세션으로 사용자 ID를 결정한다. 클라이언트가 보낸 사용자 ID를 그대로 신뢰하지 않는다.
- Context와 승인 관련 캐시를 사용자·대화 조합으로 구분한다.
- 대화 조회, 질문, 충전 갱신, 승인 처리 모두에서 대화 소유자를 검사한다.
- `/api/health`의 사용자 ID와 브라우저 기록 저장 키도 현재 접속자 기준으로 맞춘다.
- 실습 범위를 브라우저별 익명 세션으로 잡을 수 있다. 로그인 계정으로 기기 간 같은 사용자를 식별하는 기능과는 구분해 설명한다.

완료 기준: 서로 다른 브라우저 세션에서 A가 선호를 저장·삭제해도 B의 선호에 영향이 없고, B가 A의 대화 ID·승인 ID를 요청해도 조회·실행되지 않는다.

## E 담당 — 통합 시연과 발표 근거

- 계획 선택 → 확정 → 지도 → 다른 목적지 선택 → 이전 목적지 재선택.
- 선호 저장 요청 → 거절 시 미저장 / 승인 시 저장 → 새 대화에서 반영 → 삭제.
- 승인 중복 클릭·만료를 확인한다. 두 사용자 격리 시연은 보석님 구현이 반영된 뒤 함께 확인한다.
- 발표에서는 단기 기억은 `InMemorySaver`, 장기 선호는 사용자별 JSON임을 정확히 설명한다. 현재 구현을 LangGraph Store로 소개하지 않는다.
- E 담당 슬라이드는 승인 전후, 실제 저장 내용, 미들웨어가 막은 사례, 사용자 격리 결과를 중심으로 준비하고 F에게 취합한다.

현재 Python 전체 테스트 150개 통과. 브라우저 검증은 테스트 API 응답을 사용하며 실제 TMAP 지도·현대차 연동의 성공을 뜻하지 않는다.
