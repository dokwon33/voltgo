# C · 이도권 · TMAP 장소 검색

> 담당 도구: `find_station`, `search_nearby_places`
> 핵심 과제: TMAP **통합검색** / **주변(카테고리) 검색** 연동, **카테고리 매핑**, **500m 필터**
> 브랜치: `feat/tmap-places`

---

## 1. 파이프라인에서 내 위치

```
[B] get_charging_status / calculate_time_budget
        │  (충전소 이름 or 좌표, 가용 시간)
        ▼
[C] find_station ──► 충전소 좌표 확정
        ▼
[C] search_nearby_places ──► 500m 안의 후보 장소 목록
        ▼
[D] get_walking_routes / select_feasible_plans ──► 보행 왕복 시간 계산 → 복귀 가능 판정
```

- **입력 받는 쪽**: B (충전소 정보), A (에이전트가 사용자 의도 → 카테고리 전달)
- **출력 넘기는 쪽**: D (후보 장소 좌표 → 보행 경로 계산)
- 👉 C가 파이프라인 **상류**이므로 `Place` 출력 형식은 **C가 정의하고 D가 맞춘다**
  → 출력 형식(필드명·좌표계 WGS84·거리 단위 m)을 **가장 먼저 확정해서 D에게 공유**하는 게 1순위

## 3. 도구 설계 초안

> 최종 필드는 A가 동결한 `schemas`를 따른다. 아래는 협의용 초안.

### `find_station`

| 구분 | 필드 | 설명 |
| --- | --- | --- |
| 입력 | `query: str` | 충전소 이름 또는 주소 (예: "현대 EV 스테이션 강동") |
| 출력 | `name`, `lat`, `lon`, `address`, `poi_id` | 충전소 정보 |
| 사용 API | 통합검색 | 결과가 여러 개면 가장 정확한 1개 또는 후보 목록 반환 (A와 협의) |

### `search_nearby_places`

| 구분 | 필드 | 설명 |
| --- | --- | --- |
| 입력 | `lat`, `lon` | 충전소 좌표 |
| 입력 | `category: str` | 사용자 의도 카테고리 (예: "식사", "카페") |
| 입력 | `radius_m: int = 500` | 도보 반경 (기본 500m) |
| 출력 | `list[Place]` | `name`, `lat`, `lon`, `category`, `distance_m`, `address`, `poi_id` |
| 사용 API | 주변 카테고리 검색 | 받은 결과를 **클라이언트에서 500m 필터** |

### 카테고리 매핑 초안

| 사용자 의도 | TMAP 검색 카테고리 (확인 필요) | 예상 체류 시간 (D와 협의) |
| --- | --- | --- |
| 식사 / 밥 | 음식점, 한식, 분식, 패스트푸드 | 15~25분 |
| 커피 / 카페 | 카페 | 10~20분 |
| 간단한 쇼핑 | 편의점 | 5분 |
| 장보기 | 마트, 슈퍼마켓 | 15분 |
| 약 | 약국 | 5분 |
| 화장실 | 공중화장실 | 5분 |

### 왜 500m인가

- 성인 보행 속도 약 4~5km/h → 500m ≈ **편도 6~7분 / 왕복 약 13분**
- 충전 30~40분 중 왕복 13분 + 체류 15분 + 버퍼 5분 ≈ 33분 → 현실적인 상한
- 단, 실제 보행 거리는 직선거리보다 길다 → 최종 판정은 D의 **보행 경로** 결과로 한다
  (500m 필터는 D의 경로 API 호출 수를 줄이는 **1차 필터** 역할)

| 항목 | 결과 |

### 반경 자동 조정 (2026-09-11, `feat/c-adaptive-radius`)

| 항목 | 내용 |
| --- | --- |
| 공식 | `(가용 − 체류) ÷ 2 × 70m/분 ÷ 1.3` → 500~1000m (`core/place_policy.auto_max_dist_m`) |
| 가용 시간 | B 의 `TimeBudget.return_deadline` − 지금 (D 판정과 같은 기준). B 코드 변경 없음 |
| 체류 시간 | 사용자가 말했으면 `search_nearby_places(dwell_min=...)`, 아니면 카테고리 기본값 |
| 줄이지 않는 이유 | 검색 시점엔 체류 기본값을 쓰는데, 그걸로 반경을 줄이거나 검색을 막으면 사용자가 나중에 체류를 짧게 말했을 때 가능한 후보가 이미 빠진다 (B 테스트 c028 이 이 경우를 잡아냄) |
| 지정값 | 모델이 `max_dist_m` 을 주면 자동값보다 우선 (결과 없을 때 1000m 재검색) |
| 남은 확인 | 조영우님: `available_sec` 의미 유지 여부, 추정값(`energy_power`)일 때 보수 적용 여부 / 우회 보정 1.3 실측 보강 |

### 반경 넓히기 재사용 (2026-09-11, `feat/c-widen-cache`)

| 항목 | 내용 |
