## 2. 이번 승인 정책 변경 — 설계서에 우선 반영

| 설계서 위치 | AS-IS | TO-BE |
| --- | --- | --- |
| 1장 MVP / 성공 기준 | 승인 없이 `confirm_plan`·`save_preferences` 실행 0건 | 사용자가 계획을 선택하면 현재 시각·충전 상태로 재검증 후 확정한다. 별도 승인 화면은 선호 저장에만 사용하며, 승인 전 저장은 0건이어야 한다. |
| 2.2 동작 흐름 | 추천 → 승인 → `confirm_plan` | 추천 → 사용자 선택 → `confirm_plan` 재검증 → 확정 또는 재계획. 선호를 기억해 달라는 별도 요청은 `save_preferences` → 승인 대기 → 승인 후 저장으로 처리한다. |
| 2.3 시스템 프롬프트 | 계획 확정과 선호 저장은 각각 승인을 받는다 | 후보를 고른 발화로 계획 확정을 요청한다. `confirm_plan`의 성공을 확인한 뒤 확정 안내를 한다. 선호 저장은 별도 승인 후 실행한다. |
| 조건 변경 예시 | 체류시간 변경 → 재계산 → 바뀐 계획 승인 | 체류시간 변경 → 재선별·버전 갱신 → 가능한 후보 제시. 사용자가 선택하면 최신 조건으로 재검증한다. 이전 버전의 후보는 확정하지 않는다. |
| 2.5 `confirm_plan` | 승인받은 계획을 확인하고 승인·권한·버전을 검사 | 선택한 `plan_id`와 `version`, 후보 생성 후 경과시간을 확인한다. 최신 충전 상태·현재 시각으로 시간 예산을 다시 계산해 복귀 가능할 때만 확정한다. 별도 HITL 승인은 없다. |
| 3.1 승인 상태 | 사용자·thread·계획 버전에 맞는 승인 관리 | HITL 요청은 checkpointer의 thread에 남고 같은 thread로 재개한다. `Session.approval_requested_at`은 선호 저장 승인 요청 시각이다. 계획 버전 검증은 `confirm_plan`이 별도로 수행한다. |
| 3.2 HITL 대상 | `confirm_plan`, `save_preferences` | `save_preferences`만 interrupt한다. `confirm_plan`과 명시적 삭제 요청의 `delete_preferences`는 추가 승인 없이 실행한다. |
| 3.2 만료 기준 | 후보 생성 후 2분이 지나면 확정 거절 | 선호 저장 승인 요청 후 **120초 초과**면 `APPROVAL_EXPIRED`로 저장하지 않는다. 계획 후보 생성 후 **300초 초과**는 별도의 `STALE_CANDIDATE`다. 5분 이내 후보도 현재 복귀 가능 여부를 재검증한다. |
| 3.3 중복 처리 | request_id를 확인하여 동일 승인 요청은 기존 결과 반환 | 현재 계획 확정의 중복 키는 `plan_id:version`이다. 같은 후보·버전 재확정은 기존 결과를 반환한다. 이미 끝난 승인 재개는 `NO_PENDING_APPROVAL`로 거절한다. 별도의 request_id 기반 처리는 구현하지 않았다. |
| C002 | 승인 뒤 계획을 한 번 기록 | 후보 선택 후 추가 승인 화면 없이 재검증하여 확정 결과를 기록한다. |
| C006 | 승인 시각이 늦어져 재계획 | 사용자가 늦게 선택하여 가용 시간이 줄면 `confirm_plan`에서 복귀 가능성을 다시 검사하고 실패한 후보는 확정하지 않는다. |
| C016 | `confirm_plan` 승인 거절 / 2분 초과 승인 | `save_preferences` 승인 거절 / 승인 요청 후 121초에 재개했을 때 저장되지 않는지 확인한다. 120초는 허용 경계다. |
| C018 | 동일 request_id 승인 재전송 | 같은 후보·버전의 확정 재요청과 같은 thread의 중복 승인 재개를 구분해 검증한다. |

동시에 `confirm_plan`과 `save_preferences`가 제안되면 HITL은 저장 요청 하나만 승인 대상으로 표시한다. 다만 LangChain은 해당 도구 묶음을 승인 응답까지 대기시킨다. 선호 저장을 거절해 재개하더라도 선택한 계획은 재검증 후 확정할 수 있다.

## 3. 구현 설명을 실제 코드에 맞출 부분

| 설계서 위치 | AS-IS | TO-BE / 코드 근거 |
| --- | --- | --- |
| 1장 시연 범위 | CLI만 구현, 웹 화면 제외 | CLI를 유지하고 별도 브랜치에 브라우저 시연 화면을 추가한다. Python HTTP 서버가 동일한 `ask()` / `decide()`를 호출한다. 웹 서버용 별도 프레임워크는 없다. |
| 3.1 단기 기억 | 단기 기억을 thread별 InMemorySaver에 보관 | 대화 메시지·중단 지점은 InMemorySaver, 후보·시간 예산·승인 시각 등 업무 값은 `Context.session`에 보관한다. 실행기가 thread별 Context를 유지해야 하며 재시작 후 대화·승인은 복원되지 않는다. |
| 3.1 장기 기억 | 사용자 namespace / Store | LangGraph Store를 직접 연결한 구현이 아니라 **로컬 JSON 어댑터**다. `user_id` 접두사와 해시로 파일을 구분하고, 읽을 때 파일 내부 사용자 ID를 재검사한다. 승인된 카테고리·체류시간·동의 시각만 저장한다. |
| 3.2 Middleware | 승인·재시도·호출 제한을 설계 수준으로 설명 | `after_model`은 등록 역순이므로 승인 시각 훅을 HITL 뒤에 등록해 interrupt 전에 실행시킨다. 모델 8회·도구 12회·외부 API 24회 한도를 두며 모델 재시도도 예산에서 차감한다. |
| 3.3 권한 설명 | 사용자별 승인·권한 검증 | 현재 시연의 user_id는 실행기가 제공한다. JSON 파일 격리는 구현했지만 로그인·다중 사용자 인증을 구현한 것은 아니다. |
| 4장 현재 검증 상태 | 기본 테스트 36개, 승인 재개 검증 필요 | E 수정 브랜치 기준 `env -u PYTHONPATH .venv/bin/python -m pytest -q -p no:cacheprovider`: **108 passed**. 실제 ask/decide와 HITL을 실행하되 모델은 ScriptedModel, API는 Mock으로 대체했다. Pydantic의 ToolRuntime 직렬화 경고 24건이 남아 있다. |

## 5. 발표·문서에서 유지할 한계

- 남은 충전 시간과 체류시간은 입력·추정에 의존한다. ‘코드로 계산’과 ‘실제 충전 완료 시각 보장’을 구분한다.
- 선호 저장의 승인·거절·만료는 실제 에이전트 그래프로 검증했다. 실제 LLM과 실계정 API를 이용한 종단 시연 결과로 표현하지 않는다.
- 다른 팀원의 열린 PR을 읽고 정리한 내용은 현재 main 구현 완료 목록에 포함하지 않는다.
- 웹 화면과 이 문서를 반영한 DOCX·PDF 재발행은 별도 작업이다. 제출용 원본은 그대로 유지한다.
